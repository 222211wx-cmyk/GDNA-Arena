---
name: Session persistence & username login
description: Why sessions persist in Postgres and citizen authentication uses username plus password without email
---
- Sessions live in a `user_sessions` Postgres table (connect-pg-simple). **Why:** in-memory sessions were wiped on every republish/restart, logging out every citizen — the owner's biggest production complaint.
- `createTableIfMissing` of connect-pg-simple is broken in the bundled (esbuild) prod build — it reads `table.sql` from disk. The table is created manually at startup in app.ts. Keep it that way.
- Usernames are trimmed on register/login and matched case-insensitively; the database enforces case-insensitive username uniqueness. **Why:** whitespace/case mismatches must never force citizens to create duplicate accounts.
- FINAL login design (owner decision, Aug 20, 2026): username + password only. Citizen registration/login must never request email, send verification or recovery codes, or depend on Resend/SMTP. Register → logged in instantly; remember-me = 30d rolling cookie; password change only from settings while logged in.
- Legacy/system rows may retain private internal email values because Star identities and old database constraints use them, but those values must never appear in citizen auth payloads or UI. **Why:** preserve system-account compatibility without reintroducing citizen email dependency.
- Password change deletes ALL of the user's rows from `user_sessions` before re-establishing the caller's session. **Why:** a stolen session must not survive a credential change.
- Login/register regenerate the session ID after credential verification (anti session-fixation), login errors are one generic bilingual AR/FR message (anti account-enumeration), and production refuses to start without `SESSION_SECRET` (no forgeable fallback).
- Twilio/SMS/WhatsApp/2FA and email verification are permanently banned for citizen authentication. The obsolete verification column and code tables are removed at API startup.
- api-server tsconfig uses TS project references to lib/db — after changing lib/db schema, run `npx tsc -b lib/db` or api-server typecheck sees stale types from `lib/db/dist/*.d.ts`.
- Expo session-cookie storage must serialize reads, writes, and clears and bind them to an auth generation; never render a cached user before `/auth/me` verifies the cookie. **Why:** an older AsyncStorage write can finish after logout and resurrect a former session, while discarding the current cookie before login prevents server-side revocation. **How to apply:** invalidate stale writes synchronously, preserve the current cookie through login/register so the server rotates it, clear immediately on logout, and recheck generations after awaited storage writes.
- **How to apply:** any new auth-adjacent code must use username + password, never add a citizen email field or mail provider, normalize usernames consistently, keep sessions in Postgres, regenerate sessions on privilege change, and keep auth errors non-enumerating.
