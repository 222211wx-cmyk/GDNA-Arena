---
name: Session persistence & username login
description: Why sessions persist in Postgres and citizen authentication uses username plus password without email
---
- Sessions live in a `user_sessions` Postgres table (connect-pg-simple). **Why:** in-memory sessions were wiped on every republish/restart, logging out every citizen — the owner's biggest production complaint.
- A transient auth-check failure is not logout; only an authoritative unauthorized response clears verified identity. **Why:** network/server failures had been presented as needing registration again. **How to apply:** gate initial verification, but keep calls and conversations mounted during routine refreshes and offer retry without erasing the session.
- `createTableIfMissing` of connect-pg-simple is broken in the bundled (esbuild) prod build — it reads `table.sql` from disk. The table is created manually at startup in app.ts. Keep it that way.
- Usernames are trimmed on register/login and matched case-insensitively; the database enforces case-insensitive username uniqueness. **Why:** whitespace/case mismatches must never force citizens to create duplicate accounts.
- Citizen registration/login uses username + password, with immediate login after registration and no email or Resend/SMTP dependency. **Why:** the owner rejected repeatedly enrolling citizens and requiring email to enter the messenger.
- Device sign-in should persist by default with a long-lived rolling lifetime, while retaining an explicit short-session opt-out. **Why:** on 2026-10-01 the owner repeated the requirement to enter once on the same device, superseding the former 30-day remembered-login policy. **How to apply:** preserve logout/password-change revocation; never promise persistence after cookie deletion, expiry, or device loss, and never revive an expired session. Ambiguous legacy short sessions must retain their prior opt-out rather than guessing consent.
- Legacy/system rows may retain private internal email values because Star identities and old database constraints use them, but those values must never appear in citizen auth payloads or UI. **Why:** preserve system-account compatibility without reintroducing citizen email dependency.
- Password change deletes ALL of the user's rows from `user_sessions` before re-establishing the caller's session. **Why:** a stolen session must not survive a credential change.
- Login/register regenerate the session ID after credential verification (anti session-fixation), login errors are one generic bilingual AR/FR message (anti account-enumeration), and production refuses to start without `SESSION_SECRET` (no forgeable fallback).
- Do not introduce SMS/WhatsApp/email verification into ordinary citizen sign-in. **Why:** the owner rejected these dependencies; a later lost-device recovery request does not select a delivery channel or authorize weakening ownership checks. **How to apply:** treat recovery separately from normal sign-in and never reset credentials merely from a claimed username.
- Forgotten-password recovery now explicitly uses SMS to a previously verified, account-bound phone. **Why:** on 2026-10-01 the owner expressly required SMS OTP recovery, superseding the earlier recovery/SMS prohibition while preserving ordinary username/password login. **How to apply:** do not ask again whether SMS is wanted; require authenticated password re-verification to enroll a number, fresh phone proof and atomic single-use consumption to reset, and revoke old sessions. Never infer ownership from an unverified profile phone.
- Reuse the existing Firebase project for recovery rather than adding an unrelated SMS provider. **Why:** the owner insists on using the services already supplied. Public-key verification of Firebase phone proofs is independent of privileged FCM sending credentials; recovery readiness must not be tied to call-push readiness. **How to apply:** keep phone verification isolated from call authentication, and distinguish valid local configuration from console provider/billing/region setup and actual SMS delivery.
- api-server tsconfig uses TS project references to lib/db — after changing lib/db schema, run `npx tsc -b lib/db` or api-server typecheck sees stale types from `lib/db/dist/*.d.ts`.
- Expo session-cookie storage must serialize reads, writes, and clears and bind them to an auth generation; never render a cached user before `/auth/me` verifies the cookie. **Why:** an older AsyncStorage write can finish after logout and resurrect a former session, while discarding the current cookie before login prevents server-side revocation. **How to apply:** invalidate stale writes synchronously, preserve the current cookie through login/register so the server rotates it, clear immediately on logout, and recheck generations after awaited storage writes.
- **How to apply:** any new auth-adjacent code must use username + password, never add a citizen email field or mail provider, normalize usernames consistently, keep sessions in Postgres, regenerate sessions on privilege change, and keep auth errors non-enumerating.
